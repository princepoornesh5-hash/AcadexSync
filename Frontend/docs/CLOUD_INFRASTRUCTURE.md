# Acadex Cloud Infrastructure

This document outlines the implemented cloud architecture for the Acadex platform, including Firebase Storage, Firebase Cloud Messaging (FCM), and Cloud Functions (including the AI backend).

## 1. Firebase Storage Architecture

Firebase Storage is utilized for persisting and serving files for the Acadex platform. Currently, it is strictly scoped to Academic Notes published by Faculty, but the underlying abstraction supports profile images, certificates, and generic files.

### 1.1 Storage Paths
Files are logically grouped by tenant (college), department, or global namespaces to enforce isolation.

**Storage Path Format for Notes:**
`colleges/{collegeId}/faculty/{facultyUid}/notes/{fileName}`

### 1.2 Storage Rules
Access to Storage is enforced heavily through Firebase Storage Rules, which guarantee that backend boundaries are not bypassed by direct URL manipulation.

- **Read Access:** Authenticated users (students, faculty, admins).
- **Write Access:** Authenticated owner (Faculty uploading their notes).
- **File Validation:**
  - Size Limit: Maximum 25 MB per Note attachment.
  - MIME Restrictions: Executable file types (`.exe`, `.sh`, `.bat`, `.apk`, etc.) are explicitly denied.

### 1.3 Upload Workflow
1. Faculty selects a Note and attaches a valid file (`.pdf`, `.jpg`, `.doc`, etc., max 10MB checked locally).
2. The `FirebaseFileStorageRepository` validates size and MIME type on the client side.
3. The file is uploaded to the generated `colleges/{collegeId}/faculty/{uid}/notes/` path.
4. If the upload succeeds, the Storage metadata is mapped into a `StoredFile` object containing a `downloadUrl`.
5. The `NoteModel` is saved to Firestore. If Firestore saving fails, a rollback deletes the orphaned Firebase Storage object to prevent dangling resources.

### 1.4 Download Workflow
1. The Student accesses the `NoteDetailScreen`.
2. For attached files, a "Download / View Original File" button is provided.
3. The URL is resolved via the `url_launcher` package.
4. On Web, `url_launcher` correctly targets the download URL to initiate a native browser download/preview.

## 2. Firebase Cloud Messaging (FCM) Architecture

FCM is used to deliver real-time push notifications across Web and Mobile, supplementing the persistent in-app Firestore Notification history.

### 2.1 Token Management
- **Registration:** Handled on successful user login via `AuthNotifier`. 
- **Persistence:** Tokens are appended to an `fcmTokens` array on the user's document (`users/{uid}`).
- **Cleanup:** Tokens are cleanly removed from the array when the user logs out, preventing stale push notifications to inactive devices.

### 2.2 FCM Delivery Workflow
1. An Application Event occurs (e.g. Faculty publishes a Note).
2. The `NotificationService` generates `NotificationModel` documents in Firestore.
3. A Firebase Cloud Function (`onNotificationCreated`) listens to `colleges/{collegeId}/notifications/{notificationId}`.
4. The Cloud Function performs targeted Fan-Out (e.g. mapping `sectionId` to a list of users, fetching their FCM Tokens).
5. The Cloud Function securely triggers the Firebase Admin SDK to push the payload to the devices.

## 3. Cloud Functions & AI Backend

Cloud Functions are used to secure privileged backend operations, preventing client-side access to Firebase Admin SDK or AI Service Credentials.

### 3.1 `askAssistant` (AI Backend)
The AI Assistant provides intelligent, context-aware answers to Students and Faculty using Google's GenAI model.

- **Trigger:** Firebase HTTPS Callable Function.
- **Authorization:** Only authenticated users can call the function.
- **Role-Aware Context Building:**
  - The Cloud Function securely retrieves the caller's Tenant (`collegeId`) and `role` via Custom Claims or Firestore lookup.
  - Context is gathered on the server. For example: A Student's context fetches only their attendance; a Faculty's context fetches their assigned subjects.
- **Model Execution:** A zero-trust execution model is used. The AI receives the strictly scoped context and the user query, and is instructed to never hallucinate.
- **Security:** The Gemini API Key and initialization reside entirely on the server. Flutter clients only receive the sanitized output text.

### 3.2 Known Limitations & Deployment Requirements
1. **Billing:** Cloud Functions require the Blaze Pay-as-you-go plan on Firebase.
2. **File Picker WASM limitation:** The `file_picker` package relies on dart:html abstractions which prevent pure WebAssembly compilation (`flutter build web --wasm`). JS compilation (`flutter build web --release`) works perfectly and is fully supported.
3. **Environment Credentials:** The Cloud Environment must be initialized with the `GOOGLE_API_KEY` for the GenAI SDK, or use GCP Default Credentials.
